Six stages · who acts

1 · Frame

Main selects one playbook, captures all requested outcomes and discovers with find (-k synonyms, repeated until no new files), then lsp, ast_grep and grep/glob. Kiss removes unnecessary work/questions, never requested behaviour. Read-only scout maps genuinely unknown ownership.

Calls out: regression-coverage (bug) · clean-cutovers (refactor) · setup-repo-proofs and verification-surface (project setup)

2 · Spike

Main fetches the resolved remote default and creates a detached tree at ~/worktrees/<repo>/spike-<slug>. Task performs the bounded experiment; main saves the report before tree removal. Reproduction and setup inventory are mandatory; other spikes answer remaining questions. Spike code never lands.

Calls out: git-tool (remote/default) · flakes (intermittent bug) · setup-repo-proofs Steps 0–4 (setup inventory, dry run)

3 · Plan

Main maps criteria to named proofs, each an outcome test or journey linked from a feature-map entry. No feature map routes to project setup first. Draft until spike answers land; missing proof surfaces are first tasks. Each multi-phase unit, including final flag removal, has its own manifest and PR.

Calls out: tiers · case-selection · suite-budget · setup-repo-proofs Step 5 approval (setup)

4 · Implement

Prerequisite: a record with valid controls. Missing controls route to owner-approved project setup (setup-repo-proofs). Main creates the agent/<slug> branch at <worktree.base>/<repo>/<slug> (~/worktrees/<repo>/<slug>); rails refuse any other git worktree add target. After each edit, rails run harness omp-guardrails path-check with the record as config. At each agent commit, rails refuse changes to the record's ownerOnlyPaths, run harness path-check, then required repo checks.commit, then the harness checks over the whole repo; any finding blocks the commit.

Proof task writes proofs and the map entries that link them, uncommitted → main freezes (refuses unlinked proof files) → separate implementation task (configured task model) commits proofs with the greening change, pushes, authors the body, opens the PR and waits for exact-head CI. Main never commits.

Freeze runs the optional checks.format formatter first and hashes the formatted bytes, reporting files it changed for the writer to commit. One rule for every proof: red at base (any failing run; infrastructure is not red, and red containing the profile's doctor marker is refused). A PR with no behaviour change (refactor, docs, setup without new controls) freezes no proofs.

Discoveries: unplanned user-facing behaviour → implementation adds the map entry and outcome test → main re-freezes (red at base) → implementation resumes. Map sweep before the PR: each behaviour the diff adds or changes, with a concrete source path, that no changed map doc covers gets a map entry and a test, then a re-freeze. Entries and tests only, never review findings.

Dependency advisories: a commit blocked by SECURITY.dependency-audit stops implementation. dependency_audit_findings parses the gate output; one read-only task per advisory gathers evidence; triage_advisories rates severity with the calibrated jev-actions dependency-severity judgment and a fixed rubric. MAL- packages are critical in code. High, critical, no-fix or pinned-dependent-blocked advisories halt to the owner; low and medium advisories with unblocked fixes are upgraded in the flow. Blocked fixes need a dated owner exception naming the blocker, exact constraint and HTTPS evidence URL.

Designer owns presentational work and scores 10 principles, each 0–2, inspecting screenshots—not a ten-point total.

Calls out: branch-and-integrate · pr-description · proof brief: case-selection, naming-and-layout, outcome-tests, tiers (plus property-tests, determinism, behaviour-and-statistics, verification-surface when applicable) · implementation brief: implementation-integrity, structure-and-grouping, naming, before-commit · handoff (rails): before-commit · advisories: jev-actions

5 · Verify

Main confirms the writer has no pending edits, then calls prove() on the PR's current head. It checks four things: the record's required CI context is green on the exact head, rename-residue --base <parent> --head <head> leaves no finding, every feature-map doc changed in the PR links a frozen proof, and every frozen proof is unchanged and passes at head (twice; journeys 3 times). With no proofs and no map change it still checks CI and rename residue. This is the principles 5/7 exception in ADR 0003.

It writes <git-common-dir>/omp-prove/<head>.result.json and posts the result on the PR. Main then calls async structure_review() for the same range: isolated Git-object extraction, eight structure/naming questions (prefix only with eligible clusters), raw scores in <git-common-dir>/omp-structure/<head>.json, and one updated findings comment. Provisional decisions and recorded infrastructure errors never affect prove or merge. Ready findings set halt and hard-block merge via rails. Both exact-head files are required, even with all decisions provisional. No review agent or status posting. A rebase/update repeats both calls on the new head.

Calls out: verify-loop · jev-actions (structure/naming judgment)

6 · Integrate

Main merges the head under merge-and-recover, respecting agentMerge: disabled. With dynaflows on, rails require exact-head CI green, prove status: pass and structure halt: false. Missing, corrupt or wrong-head files block. Fix ready findings and rerun both helpers on the new head. Wait for MERGED.

Repository-specific target or merge-method exceptions live in that repository's project instructions.

Calls out: merge-and-recover · codify-omp-workflow-corrections (repeated incident class)

Harness / repo boundary

A repo never depends on, contains or mentions omp or dynaflows. It keeps the code, tests and controls the project wants without the harness. Opinions and their checks live in the harness; per-repo settings live in a personal record.

Outcome-first verification

test-guidance supplies generic testing practice, usable without dynaflows. Dynaflows proofs owns binding policy, freezing and profile location; test enforcement maps deterministic rules. The record's profile.md supplies values and may tighten them. Plan reads tiers, case selection and suite budgets.

User-visible work without a verification surface first completes owner-approved Project setup (setup-repo-proofs) in one or more Step 0 modes: greenfield (no record, no repo checkers); adopt (repo checkers hold, or could hold, rule families the record does not yet give them; missing rules land in the repo by PR, never as a harness copy); extend (a record missing one part, such as the surface). Guarded repos use surface-only extend mode. An approved no-runnable-app exemption does not divert config or skill work. Setup demonstrates a broken variant in scratch, then discards that code. The feature map must exist before any TDD proof. Proof tasks write the lever, runner-invoked journeys and the map entries linking them, and freeze them together; like new-control canaries, they fail at base and pass at head. Implementation writes map, profile and guardrails, in that order; Step 5 approval remains mandatory. The profile and guardrail settings go in the local record, never in the repo.

Outcome tests drive public entry points; property tests cover pure cores. Every proof, lever journeys included, fails at base and passes at head; doctor/environment failures are not accepted red. Proof briefs read case selection, naming/layout, outcome tests, tiers and profile, plus property, determinism, statistics and surface guidance when applicable. Proofs come only from outcome tests and journeys linked from the feature map, the maintained verification source. Implementation edits product code and map docs, not frozen lever bytes; a new proof enters only through a discovery or map-sweep re-freeze.

T1 has no processes or network; T2 owns seams and boundary-crossing journeys; T3 owns agent exploration and live paid calls. Commit runs static checks, T1 and affected T2; CI runs T1 + T2; nightly adds T3 on scheduler-enumerated active branches. Approved per-machine timing limits run on the local commit gate only; CI never measures or reports test timing. First limits and raises need approval.

CI runner and Jev are not alternate merge authority

The record's gate.json ci object is authoritative. ci.requiredContext names the commit-status context or check run that must be green on the exact head, whoever posts it. ci.runner names a role, such as ci-gate or github-actions. Per-machine ci-runners.json, written by device rollout, maps each role to submit, wait, status and logs commands. The writer submits and waits through scripts/ci-runner.py with that role; workflow and rails code hold no host names. Another runner's success never substitutes for a missing required context; escalate the incident under git-tool.

Jev TTSR warnings can trigger at any stage on a main-agent reply: regression coverage, clean cutovers, flakes and measured claims. Their placement is not a stage gate. Subagents get explicit references in briefs and their own rails checks. Deterministic checks precede Jev single-state judgement.

Principles · different kinds of enforcement

The design rubric has ten principles scored 0–2 each; the workflow principles below explain the system, not a second design rubric.

  1. Proof over opinion.

    Check: deterministic proof execution; agent opinion review is not evidence.

  2. Questions before experiments. Frame only plan-changing uncertainty; save scratch evidence before removal.
  3. Proofs before implementation.

    Check: freeze refuses proofs the feature map does not link and shows red at base; prove shows the same frozen bytes green at head and blocks changed map docs without a proof.

    Instruction: ordered proof/main-freeze/implementation actors.

  4. Events trigger checks. Commit, PR and CI events run checks; pulling existing commits in runs nothing extra.
  5. Deterministic first. Infrastructure failure is not red evidence; judgement cannot turn it into pass.
  6. Governed structure and tests.

    Check: harness path-check with record config, then repo commit controls and whole-repo harness checks; repo CI stays repo-owned.

    Hard block: missing required references or unresolved path failures.

  7. Short-lived units. Independent units land independently; final flag removal is its own unit, not an afterthought.
  8. One merge boundary. Exact-head green CI plus, with dynaflows on, prove pass and structure halt false in both exact-head files; ready findings hard-block via rails. Disabled agentMerge still needs owner approval.
  9. Delegate implementation. Main coordinates and runs prove(); the writer commits through the commit checks and delivers the ready PR.
  10. Least correct work. Cut needless work, never requested behaviour; remove obsolete paths in the canonical cutover.
